# scripts — командные утилиты

Всё, что запускается из терминала помимо основного приложения: отладка, эксперименты, замеры. Тонкие обёртки над `mir` — никакой логики здесь быть не должно.

Отдельная папка нужна по практической причине: во время разработки GUI ещё нет, а конвейер гонять надо. И для экспериментальной главы прогоны удобнее делать скриптом, а не кликами.

## Готовые

```
scripts/
├── ingest_cli.py    этап 2: ссылка или файл → видео и аудиодорожка
├── vision_cli.py    этап 3: разбор видеоряда, картинки, метрики
├── audio_cli.py     этап 4: ноты по звуку, атаки, темп, рассинхрон
├── fusion_cli.py    этап 5: слияние каналов, MIDI для проверки на слух
├── ablation.py      слияние против одиночных каналов на известном ответе (NF-10)
└── bench_core.py    сравнение нативного ядра с numpy
```

Через `run.cmd` всё это запускается одной командой с правильным интерпретатором: `run demo`, `run audio demo`, `run audio analyze video.mp4`, `run fuse …`, `run ablation`.

## `vision_cli.py`

Проверка этапа 3 глазами: разметка клавиатуры поверх кадра, найденные ноты в виде фортепианного валика, метрики MIREX.

### Самопроверка на синтетическом ролике

```bash
python scripts/vision_cli.py demo
```

Соберёт ролик из заранее известного списка нот, разберёт его и сохранит в `build/vision_demo/`:

* `layout.png` — найденная клавиатура поверх кадра: белые клавиши обведены, чёрные залиты, каждое «до» подписано. Съехавшая разметка видна мгновенно;
* `roll.png` — эталон и результат друг под другом.

Эталон здесь точен по построению: ролик рисуется из него же, ручная разметка не нужна и не может ошибиться.

Условия варьируются ключами:

```bash
python scripts/vision_cli.py demo --scheme dark
python scripts/vision_cli.py demo --noise 6 --glow --width 854 --height 480
python scripts/vision_cli.py demo --scheme mono --watermark "PIANO TUTORIAL"
```

| ключ | что проверяет |
|---|---|
| `--scheme dark` | тёмная тема — половина визуализаторов |
| `--scheme mono` | одноцветная схема: руки неразличимы, ноты обязаны найтись |
| `--noise` | шум сжатия, первая из заявленных проблем проекта |
| `--glow` | свечение вокруг блоков |
| `--watermark` | логотип поверх кадра |

### Разбор своего ролика

```bash
python scripts/vision_cli.py analyze video.mp4
python scripts/vision_cli.py analyze video.mp4 --overlay layout.png --roll roll.png
python scripts/vision_cli.py analyze video.mp4 --csv notes.csv
python scripts/vision_cli.py analyze video.mp4 --truth notes.csv
python scripts/vision_cli.py analyze video.mp4 --seconds 20 --overlay layout.png
```

Заставку и титры искать не нужно: они отсекаются сами, по кадрам без клавиатуры. Ключ `--start` нужен лишь чтобы принудительно начать позже найденной границы.

В сводке строка `источник` говорит, откуда взяты ноты: «блоки над клавиатурой» (основной путь, руки исполнителя не мешают) или «подсветка клавиш» (если блоков в ролике нет — с причиной в предупреждении). Линия касания и скорость падения в этом случае измерены по самим блокам; `отсеяно дыма, искр и прочего` — сколько событий верхней полосы не дошло до нижней как падающий блок.

`--seconds N` разбирает только отрезок ролика. Клавиатуру и профиль
визуализатора при этом всё равно ищет по всей длине — медиана по кадрам
из одного места хуже убирает подсветку. Ключ нужен для первой проверки:
на пятиминутном ролике полный разбор идёт минуты, а понять, не съехала
ли разметка, можно за двадцать секунд.

Рядом с `--csv video.csv` всегда пишется `video.candidates.csv` — блоки-кандидаты: то, что датчик видел, но не смог доказать. Сами по себе это не ноты; их подбирает слияние каналов (`run fuse`), файл оно находит само.

`--csv` пишет найденные ноты, `--truth` читает эталон в том же формате и печатает метрики. Формат простой (`mir/eval/notes_io.py`, общий для всех утилит):

```csv
pitch,onset,offset,velocity,hand,source,confidence
60,0.5000,0.9000,90,RIGHT,VIDEO,1.000
```

Обязательны первые три столбца — эталон удобно размечать вручную.

Ключ `--min-f1` задаёт порог: при F1 ниже команда возвращает код 1, что позволяет ставить её в CI.

## `audio_cli.py`

Проверка этапа 4 в цифрах и на слух.

### Самопроверка на синтетике

```
run audio demo
run audio demo --bpm 140 --subdivision 4 --noise -25
```

Собирает звук из известного списка нот и печатает ошибку темпа (требование NF-08 — не больше 2 %), точность атак и оценку рассинхрона двумя способами. Сохраняет `build/audio_demo/beats.wav` — звук с наложенными щелчками на найденных долях, высокий щелчок — сильная доля. Нейросеть здесь не проверяется: синтезированный тон — не рояль.

### Разбор своего ролика

```
run audio analyze video.mp4 --no-transcribe --clicks beats.wav
run audio analyze video.mp4 --csv audio_notes.csv
run audio analyze video.mp4 --seconds 30 --start 40
run audio analyze video.mp4 --bpm 72 --clicks beats.wav
run audio analyze audio.wav --truth notes.csv --min-f1 0.8
```

Вместо файла можно дать ссылку: `run audio analyze "https://youtu.be/..."`. Ролик скачивается в кэш (`~/.mir_cache`), и повторный запуск с той же ссылкой не качает заново. То же умеют `run audio sync` и `run analyze`. Звук из видео извлекается FFmpeg во временный каталог; WAV, FLAC и MP3 читаются напрямую.

| ключ | что делает |
|---|---|
| `--no-transcribe` | без нейросети: только атаки и темп, секунды вместо минут |
| `--clicks` | WAV со щелчками на долях — **самая быстрая проверка темпа**: послушать десять секунд |
| `--onset-clicks` | WAV со щелчками на атаках |
| `--bpm` | задать темп вручную (F-31); сетка выравнивается по звуку, шаг — заданный |
| `--start`, `--seconds` | разобрать отрезок; время в результатах — время ролика |
| `--device` | `auto`, `cpu`, `cuda` |
| `--csv`, `--truth`, `--min-f1` | как у `vision_cli.py` — формат CSV общий |

### Рассинхрон звука и картинки

```
run analyze video.mp4 --csv video_notes.csv
run audio sync video.mp4 --video-csv video_notes.csv --audio-csv audio_notes.csv --aligned-csv audio_aligned.csv
```

Печатает сдвиг, уверенность и решение — применяется он или нет. Без `--video-csv` видеоряд разбирается заново, без `--audio-csv` — заново гоняется нейросеть; на полном ролике это минуты, поэтому лучше передать CSV из предыдущих команд. Без нейросети оценка идёт только по атакам и на ровном ритме честно отказывается.

### Сверка каналов без эталона

```
run audio compare --video-csv video_notes.csv --audio-csv audio_notes.csv --roll compare.png --end 40
```

Сравнивается только общий отрезок обоих каналов (видео часто разобрано с `--seconds`, а звук целиком); `--start`/`--end` сужают его ещё.

Две оценки:

* **валики** — совпадение фортепианных валиков и сдвиг по времени и по высоте, при котором оно лучше всего. Если лучше всего совпадение при сдвиге высоты, а не при нуле, — один из каналов ошибается в нотах. Длительности у верных каналов расходятся из-за педали, поэтому даже хорошее совпадение заметно меньше 1 (на Rousseau 0.67);
* **по началам нот** — P, R, F1 и средняя ошибка начала после сдвига видео на найденный рассинхрон. Звук здесь вместо эталона, его ошибки тоже входят в счёт.

Картинка `--roll` показывает оба валика на одной оси: звук зелёным, видео красным. Именно так найден дефект В-05.

### Нейросеть

```
run audio-setup            PyTorch для процессора + библиотека + веса (172 МБ)
run audio-setup cuda       то же со сборкой PyTorch для видеокарт NVIDIA
run audio fetch-model      только веса
run audio doctor           что установлено, где веса, на чём будет считать
```

## `fusion_cli.py`

Этап 5: из нот видео и нот звука — один список, с причиной по каждой ноте.

```
run fuse --video-csv video_notes.csv --audio-csv audio_notes.csv --csv fused.csv --midi fused.mid
run fuse data\videos\video.mp4 --video-csv video_notes.csv --audio-csv audio_notes.csv --midi fused.mid
run fuse "https://youtu.be/..." --midi fused.mid --roll fused.png --decisions decisions.csv
```

Файл канала, который уже есть, читается; которого нет — считается из ролика и сохраняется туда же. Поэтому после `run analyze … --csv` и `run audio analyze … --csv` слияние отрабатывает за секунду, а без них — разбирает ролик само (видео — минуты, звук на процессоре — около длительности ролика).

Что печатает:

```
рассинхрон      : +111 мс в целом; по ходу ролика от +90 до +117 мс
согласие каналов: звук подтверждает 97% нот видео, видео — 91% нот звука
ведущий канал   : видео
порог для звука : нота только из звука принимается при уверенности от 0.80
итог            : 1171 нот — оба канала 1130, только видео 32, только звук 9
принято:
    1122  оба канала: высота и начало совпали
      32  только видео: блок прошёл обе полосы датчика
       7  звук и блок-кандидат видео
       7  только звук: повторный удар, блоки в видео слились
отброшено:
      31  звук за пределами видеоряда (заставка, титры)
      44  звук: повторная атака на удерживаемой клавише
      28  звук: на октаву или дуодециму от ноты видео
      27  звук: неуверенная нота без блока в видео
```

На что смотреть: «звук подтверждает … нот видео» — на исправном ролике больше 90 %; если меньше половины, ведущим становится звук, и об этом будет предупреждение. «Видео подтверждает … нот звука» бывает заметно ниже (70 % на Interstellar) — это ошибки и эффекты звука, они перечислены в «отброшено».

Что сохраняет:

* `--midi` — итог как сыгран, без тактов и квантования. Открывается любым плеером: **самая быстрая проверка — послушать и сравнить с роликом**;
* `--csv` — итоговые ноты в общем формате; время — в шкале звука;
* `--roll` — валик: зелёным подтверждённое обоими каналами, синим только видео, оранжевым принятое из звука, серым отброшенное. `--start`/`--end` задают окно;
* `--decisions` — таблица решений: по строке на каждую исходную ноту, с причиной и уверенностью звука. Для разбора, почему нота принята или отброшена.

## `ablation.py`

```
run ablation
run ablation --seeds 10 --bars 80
```

Проверка NF-10: слияние не хуже лучшего одиночного канала. Эталон задан, каналы получены из него порчей — ошибками тех видов, что найдены на настоящих роликах (`tests/fixtures/channels.py`); печатается F1 видео, звука и слияния по семи сценариям. Код возврата 1, если слияние где-то уступило.

Это проверка логики слияния, а не замер на живых данных: модель ошибок написана по тем же наблюдениям, что и правила. Прогон на настоящем наборе с эталоном — этап 8.

## `bench_core.py`

```bash
python scripts/bench_core.py
python scripts/bench_core.py --width 1280 --height 720 --repeats 100
```

Замеряет обе ветки `mir.vision.accel` на данных реального размера. Сначала проверяет, что они дают одинаковый ответ, — иначе замер недействителен и печатается предупреждение.

Таблица из этого скрипта — прямое обоснование выбора C++ в дипломной работе. Без неё вопрос «зачем вам C++, всё же есть в Python?» останется без ответа.

## `ingest_cli.py`

```bash
python scripts/ingest_cli.py info "https://youtube.com/watch?v=..."
python scripts/ingest_cli.py get "https://youtube.com/watch?v=..."
python scripts/ingest_cli.py get ./local.mp4 --output ./work
python scripts/ingest_cli.py doctor
```

`doctor` диагностирует сеть: проверяет прямое соединение и ищет запущенный VPN-клиент. Пользователю настраивать прокси не нужно — при включённом VPN в режиме TUN прямое соединение уже работает, а если нет, адрес подбирается автоматически.

## Запланированные

Появятся по мере готовности соответствующих этапов:

| скрипт | этап | назначение |
|---|---|---|
| `transcribe.py` | 7 | основной CLI: ссылка → нотный лист |
| `evaluate.py` | 8 | метрики на всём тестовом наборе, CSV для диплома |
| `make_dataset.py` | 8 | пакетная генерация синтетических роликов из MIDI |

`ablation.py` уже есть, но пока сравнивает каналы на модели ошибок. На этапе 8 он должен получить настоящий набор с эталоном: если слияние не выигрывает у обоих одиночных каналов на живых данных, заявленная новизна не подтверждается. Лучше узнать это заранее, а не на защите.
