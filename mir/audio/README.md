# mir/audio — анализ аудиодорожки

Этап 4 конвейера. Второй, независимый от видео источник истины. Даёт то, чего видео дать не может: точное время атак, ноты за пределами кадра и темповую сетку.

## Роль в проекте

Аналоги делятся на две группы: видео-парсеры и аудио-транскрипторы. Ни те, ни другие не используют оба канала. Здесь аудио — не замена видео, а **перекрёстная проверка**:

| Что даёт видео | Что даёт аудио |
|---|---|
| Точная высота (позиция клавиши однозначна) | Точное время (шаг 8 мс против 33-40 мс) |
| Разделение рук по цвету | Ноты, не попавшие в кадр |
| Работает при плохом звуке | Работает при плохом видео |
| Длительность из длины блока | Темп и сетка долей |

## Состояние: что проверено, а что нет

| | на чём проверено | результат |
|---|---|---|
| атаки (#28) | синтетика: мелодия, случайный ритм, шум −30 дБ | полнота 1.00, задержка +10 мс, разброс 2-3 мс |
| темп (#27) | метроном 60-150 BPM, мелодии 70-140 BPM, ускорение 90→130 | ошибка ≤ 0.25 % при требовании NF-08 ≤ 2 % |
| ручной темп (F-31) | мелодия 100 BPM, задано 50 | ровно 50.00 BPM |
| рассинхрон (#29) | синтетика + собранный FFmpeg ролик mp4/AAC | сдвиг 250 мс найден с ошибкой 2 мс |
| проход нейросети (#26) | настоящая архитектура ByteDance на случайных весах | разметка **побитово** совпадает с исходной библиотекой |
| качество нейросети | — | **не проверено**: см. ниже |

**Чего здесь нет — и это важно.** Официальные веса модели (172 МБ) в среде разработки скачать не удалось: Zenodo закрыт сетевыми правилами песочницы. Поэтому проверены механика прохода, загрузка весов и постобработка — но не то, как модель распознаёт живой рояль. Синтетика для этого не годится: синтезированный тон — не рояль, и низкий F1 на нём ничего не скажет о модели. Проверка качества — прогоном на реальном ролике с эталоном (задача #13), команда в конце файла.

Опубликованное качество модели — F1 по нотам 0.968 на MAESTRO (Kong et al., 2021). Это студийные записи рояля; YouTube-ролики со сжатием звука и реверберацией дадут меньше, и насколько — покажет эксперимент.

## Как устроено

```
звуковой файл (WAV из ingest)
   │
   ├─► transcriber   нейросеть по сегментам 10 с  →  ноты, педаль
   ├─► onsets        функция новизны, пики       →  атаки
   └─► tempo         beat-tracking по той же функции → сетка долей
                     (начала нот транскрипции помогают выбрать уровень)

рассинхрон — в mir/fusion/aligner.py: он сравнивает оба канала
```

## Файлы

```
audio/
├── signal.py        звук в памяти, чтение WAV/FLAC/MP3, привязка ко времени ролика
├── onsets.py        функция новизны, атаки, подтягивание нот к атакам (#28)
├── tempo.py         темп, доли, ошибка вдвое, уверенность (#27)
├── models.py        веса модели: поиск, загрузка, проверка; выбор устройства
├── transcriber.py   проход нейросети по сегментам, перевод в NoteEvent (#26)
├── bytedance.py     адаптер модели ByteDance
└── analyzer.py      точка входа этапа: analyze_audio()
```

## Контракт этапа

```python
result = analyze_audio(
    media.audio_path,
    config,
    transcribe=True,  # False — только атаки и темп, секунды вместо минут
    force_bpm=None,  # темп от пользователя (F-31)
    start_seconds=0.0,  # разобрать отрезок; время остаётся временем ролика
    max_seconds=None,
    progress=callback,  # (Stage.AUDIO, 0..1)
    cancel=lambda: event.is_set(),
)
result.notes  # list[NoteEvent], source=AUDIO, рука не определена
result.pedals  # list[PedalEvent] — правая педаль (F-13)
result.tempo  # TempoMap
result.onsets  # моменты атак
result.warnings  # для показа пользователю
```

## `transcriber.py` и `bytedance.py` — нейросеть (#26, F-09, F-13)

Модель — High-resolution Piano Transcription (Kong et al., 2021): на входе звук 16 кГц, на выходе покадровые (100 кадров/с) вероятности начала, конца и звучания каждой из 88 клавиш, громкость и педаль. Из библиотеки `piano_transcription_inference` взяты **только архитектура и постобработка** — то, что повторять нельзя, иначе разошлось бы с опубликованным качеством. Всё остальное своё, потому что исходная библиотека для приложения не годится:

| недостаток исходной библиотеки | что сделано |
|---|---|
| веса качаются через `os.system("wget ...")` — на Windows `wget` нет, загрузка молча не происходит | своя загрузка через `urllib`, с прогрессом и отменой |
| целостность проверяется по «размер больше 160 МБ» — недокачанный файл проходит | размер до байта и MD5 из метаданных Zenodo |
| веса грузятся с `strict=False`, результат не проверяется: файл другой модели загрузится «успешно», и сеть будет выдавать мусор на случайных весах | недостающие обучаемые параметры — ошибка с понятным сообщением (тест `test_incomplete_weights_rejected`) |
| `torch.load` без `weights_only` — исполняет код из файла | сначала безопасный режим; обычный — только для файла, сверенного по MD5 |
| все сегменты ролика в памяти разом, ход работы печатается `print` | потоковый проход: прогресс и отмена после каждого сегмента |
| громкость `int(v * 128)` выходит 128 при допустимых 0..127 | ограничение 1..127 |
| нота может получить конец, равный началу | минимум один кадр (10 мс) |
| `matplotlib.pyplot` импортируется без нужды и в окне Qt поднимает свой бэкенд | бэкенд принудительно без окон |

**Сегменты.** Сигнал дополняется нулями до целого числа 10-секундных сегментов и режется с шагом 5 с. Из каждого сегмента берётся средняя половина разметки, из крайних — ещё и внешняя четверть: края сегмента модель видит без контекста и размечает хуже. Схема та же, что у авторов, — и тест `test_streaming_matches_original_library` проверяет, что разметка совпадает с исходной **побитово**.

> Первоначальный замысел был другим: резать ролик на минутные куски с перекрытием 2 с и склеивать ноты. Разбор исходного кода показал, что это не нужно и вредно. Не нужно — модель и так работает по 10-секундным сегментам, а в памяти держится только покадровая разметка, около 25 МБ на минуту звука. Вредно — нота, звучащая через стык кусков, обрезалась бы на стыке, и её конец пришлось бы угадывать. Потоковый проход по сегментам модели этой проблемы не имеет: постобработка видит непрерывную разметку.

**Уверенность ноты** — вероятность начала из самой модели в кадре атаки. Пригодится этапу 5: нота из одного канала с низкой уверенностью — кандидат на отсев.

**Устройство (NF-12).** `auto`: видеокарта, если есть CUDA и свободно не меньше 2 ГБ, иначе процессор. Замер в среде разработки (2 ядра, без GPU): 15 с звука за 20 с, то есть 1.3× реального времени при требовании NF-02 ≤ 4×.

**PyTorch не в основных зависимостях.** Он весит от 200 МБ (CPU) до 2.5 ГБ (CUDA), и правильную сборку pip сам не выберет. Без него этап работает: атаки и темп считаются, транскрипция сообщает, как её установить.

## `onsets.py` — атаки (#28)

Спектральный поток в мел-шкале, пики — атаки. Видео при 25 fps видит мир с шагом 40 мс, здесь шаг 8 мс.

**Окно 1024 вместо 2048, шаг 128 вместо 256** — по замеру на синтетике с известным ответом:

| окно / шаг | задержка | разброс | полнота |
|---|---:|---:|---:|
| 2048 / 256 (librosa по умолчанию) | +19 мс | 4.7 мс | 1.00 |
| 1024 / 256 | +14 мс | 4.5 мс | 1.00 |
| **1024 / 128** | **+10 мс** | **2.2 мс** | **1.00** |

Механизм общий, не подогнанный: поток в децибелах скачет, когда атака входит в окно, а вес окна Ханна у края мал — чем короче окно, тем раньше атака становится заметной. Остающаяся задержка ~10 мс постоянна; на нотный текст она не влияет (важны интервалы, не абсолютное время), а при сведении каналов поглощается оценкой рассинхрона.

Попутно найдена ловушка librosa: если передать в `onset_strength` готовый спектр, а не сигнал, она компенсирует задержку по окну по умолчанию (2048), а не по фактическому. Атаки уезжали на 32 мс. Теперь `n_fft` передаётся явно.

**`refine_note_onsets`** подтягивает начала нот к ближайшей атаке не дальше 50 мс — допуска MIREX: уточнение не должно превращать правильную по меркам оценки ноту в неправильную. Ноты аккорда притягиваются к одной атаке, как и должно быть.

**Две функции новизны.** Для атак — поток по спектру в децибелах: тихая атака на фоне тишины видна не хуже громкой. Для акцента (сильные доли) — поток по мощности. Замер на метрономе с акцентом: в децибелах сильная доля выходила даже *слабее* прочих (21.2 против 18.1-27.7), по мощности — вдвое сильнее (1.22 против 0.57-0.64). На мелодии с басом картина та же.

## `tempo.py` — темп (#27, F-14, NF-08)

Основа — динамическое программирование librosa (Ellis, 2007). Своё сверху:

**Переменный темп.** У librosa жёсткость 100, и на ускорении 90→130 BPM она теряет каждую десятую долю (F = 0.90). При 50 — ни одной (F = 1.00), на ровном темпе разницы нет.

**Уточнение вторым проходом.** Начальная оценка темпа по автокорреляции квантована; на шестнадцатых при 140 BPM она давала 112. Трекер с допуском выходил на верные доли, но средний темп отличался на 1.7 %. Если темп найденных долей расходится с исходной оценкой больше чем на 1 %, трекинг повторяется — ошибка падает до 0.02 %.

**Ошибка вдвое — это не ошибка.** Восьмые при 60 BPM и четверти при 120 звучат одинаково; по звуку выбрать нельзя, и MIREX считает темп верным с точностью до множителя 2 («Accuracy 2»). Решение принимается по нотной традиции: если типичная нота при найденном темпе ближе к тридцать второй, чем к шестнадцатой, темп удваивается; если ближе к половинной, чем к четверти, — делится пополам. Внутри диапазона найденный темп не трогается.

> Границы проходят посередине между соседними длительностями в логарифмической шкале, то есть с множителем √2 — это геометрия шкалы, а не подобранное число. Граница ровно на 1 доле сначала была ошибкой: метроном 90 BPM давал типичный интервал 1.0045 доли и «исправлялся» на 45 BPM.
>
> В исходном описании модуля направление было перепутано: «если ноты выходят тридцать вторыми, темп завышен». На деле наоборот — короткие в долях ноты означают, что доля взята слишком длинной, то есть темп занижен.

Ошибку, которую традиция не ловит, правит пользователь кнопками «×2» и «÷2» (F-31).

**Ручной темп** не «плывёт»: ровная сетка с заданным шагом, по звуку выбирается только сдвиг. Трекер с допуском утягивал заданные 50 BPM к 51.6.

**Уверенность** — доля долей, рядом с которыми (70 мс) есть атака. Ниже 0.5 — предупреждение «задайте темп вручную». Отдельно считается **разброс длительности долей**: на ровном темпе около 1 %, на rubato — 10 % и больше. Это только для отчёта: сетка, следующая за rubato, не ошибочна, квантизация по ней работает и при плавающем темпе.

**Сильные доли** расставляются предварительно, для 4 долей в такте: из четырёх сдвигов выбирается тот, где на первую долю приходится самый сильный акцент. Размер и затакт определяет этап 5 (#33).

**Синтетика для темпа — с акцентами на долях.** Первый вариант тестовой мелодии отмечал басом только начало такта, а ровные шестнадцатые между ними; на ней темп «ошибался» в 4/3 раза. Ошибался не трекер, а тест: у ровных шестнадцатых без акцентов любой кратный им период одинаково правдоподобен. В живой музыке доли отмечены басом и гармонией — теперь и в синтетике.

## Как проверить

```
run audio demo
```

Синтетика с известным ответом: темп, атаки, рассинхрон, плюс `build/audio_demo/beats.wav` — звук с наложенными щелчками на найденных долях. **Послушать его — самая быстрая проверка темпа:** если щелчки идут вместе с музыкой, сетка верна.

На реальном ролике (вместо `video.mp4` можно дать ссылку на YouTube в кавычках — ролик скачается в кэш один раз):

```
run audio analyze video.mp4 --no-transcribe --clicks beats.wav
run audio-setup                         один раз: PyTorch и веса модели
run audio analyze video.mp4 --csv audio_notes.csv
run audio sync video.mp4 --video-csv video_notes.csv --audio-csv audio_notes.csv
```

Подробности ключей — в `scripts/README.md`.

## Известные ограничения

* **Качество нейросети на YouTube-роликах не измерено** — нужен эталон (#13).
* **Сильные доли предварительные**, размер такта по умолчанию 4/4 — до этапа 5.
* **Педаль только правая** (демпферная) — модель других не распознаёт.
* **Пороги темпа и атак настроены по синтетике.** Механизмы, на которых они основаны, общие (длина окна, геометрия шкалы длительностей), но подтверждение на живых записях — та же задача #13.
